# Init
Init — это главный процесс, который после получения управления принимает решение о последовательности запусков сервисов с системе. Init подготавливает систему перед показом терминала или первого изображения на экране. Главный файл с описанием конфигурации Init находится по пути `/system/etc/init.cfg`. Файл представляет из себя json конфигурацию, которая содержит в себя секции import, jobs и services. 

Секция **import** описывает другие файлы `.cfg`, которые будут импортированы. 

Секция **jobs** описывает команды, которые выполняет сам init. Описанные в секции jobs команды выполняются внутри процесса init, последовательно, одна за другой. Отдельного процесса нет. Jobs имеет возможность запускаться по условия (`condition`), например при соблюдении параметра как показано в следующем фрагменте:

```json
  { "name" : "param:security.perf_harden=1",
    "condition" : "security.perf_harden=1",
    "cmds" : [ "write /proc/sys/kernel/perf_event_paranoid 3" ]
  }
```
Такая job выполняется каждый раз, когда параметр принимает это значение. Условия можно комбинировать: `boot && const.debuggable=1`.

cmds — это встроенные команды init, а не shell. Пайпов, &&, перенаправлений и переменных окружения нет. Подставляются только ${параметр}. Набор команд фиксирован: mkdir, chmod, chown, write, mount, symlink, copy, start/stop, trigger, setparam, exec, load_persist_params и т.д. Если нужна логика shell, используйте exec /system/bin/sh -c "..." или отдельный скрипт.

Секция **services** описывает процессы, которыми init управляет. Пример:

```json
{
  "name" : "watchdog_service",
  "path" : ["/system/bin/watchdog_service", "10", "20"],
  "uid" : "watchdog",
  "gid" : ["watchdog", "log", "readproc"],
  "disabled" : 1,
  "start-mode" : "condition"
}
```

Это описание демона, который init запускает через `fork/exec` и потом отслеживает: перезапускает при падении, останавливает при выключении, создаёт для него сокеты.
Основные поля:

* **path**:	бинарник и аргументы
* **uid, gid**:	от какого пользователя и групп запускать
* **start-mode**:	`boot` (рано), `normal` (по умолчанию, после `post-init`), `condition` (только по start)
* **disabled**:	не запускать автоматически
* **once**:	запустить один раз, при выходе не перезапускать
* **critical**:	если сервис падает слишком часто, перезагрузить систему ([включено, сколько раз, за сколько секунд])
* **ondemand**	запускать по требованию: при обращении к сокету или по запросу samgr для SA
* **socket**:	сокеты, которые init создаёт заранее и передаёт процессу (ueventd)
* **console**:	привязать к консоли (console = sh на tty)
* **caps, secon, apl, sandbox**:	capabilities, SELinux-контекст, уровень доступа токена, песочница
* **jobs**:	jobs, привязанные к событиям жизни сервиса

### Связь сервисов и jobs

Внутри сервиса можно указать, какую job выполнить на его событиях:

```json
{
  "name" : "my_service",
  "path" : ["/system/bin/my_service"],
  "jobs" : {
    "on-boot"  : "boot",
    "on-start" : "services:my_service_prepare",
    "on-stop"  : "services:my_service_cleanup"
  }
}
```


# Сборка
Для сборки используйте команду `make.sh rootfs_init` в контейнере. 
Для сборки конфигурационных файлов файлов init используйте команду `make.sh rootfs_services_cfg`.

Результат сборки находится по следующим путям:
* `out/oneir/startup/init/`
* `out/oneir/thirdparty/mksh/sh`
* `out/oneir/thirdparty/toybox/toybox`


### out/oneir/startup/init/
| Файл | Описание |
|---|---|
| `init` | Первый процесс системы (PID 1). Запускает и контролирует сервисы по файлам `*.cfg`, содержит сервис системных параметров, назначает сервисам права и токены, создаёт песочницы. |
| `ueventd` | Демон устройств: получает от ядра события `uevent` и создаёт файлы в `/dev` с нужными правами и владельцами (по `ueventd.cfg`). |
| `begetctl` | Утилита управления `init` из командной строки: запуск и остановка сервисов, работа с параметрами и песочницами, перезагрузка. Многие команды (`param`, `reboot` и другие) — ссылки на неё. |
| `param` | Утилита для работы с системными параметрами (`param get`, `param set`, `param ls`, `param wait`). Скорее всего, это ссылка на `begetctl` или его урезанная версия. |
| `libbegetutil.z.so` | Базовая библиотека `init`: клиентский API системных параметров (`GetParameter`/`SetParameter`), логирование и вспомогательные функции. Её используют почти все сервисы OpenHarmony. |
| `libbeget_proxy.z.so` | Клиентская библиотека для обращения к `init` из других процессов: управление сервисами, перезагрузка и другие запросы к `init`. |
| `libsystemparam.z.so` | Библиотека доступа к системным параметрам. Судя по названию, это обёртка для других компонентов. Точное назначение лучше проверить по `BUILD.gn`. |
| `libparam_watcher.z.so` | Подписка на изменения параметров: процесс получает уведомление при изменении параметра. Работает через системный сервис `param_watcher` (требует `samgr`). |

### Запуск сервисов через Init
Для запуска сервиса Init нуждается в `.cfg` конфигурационных файлов, которые описывают инструкции для инициализации сервиса, разрешения и т.д. Так же многие сервисы при старте читают свои параметры (`.para.dac` файлы). Без них они либо работают с неверными значениями, либо не получают права на запись своих параметров.

**Важно отметить**: при старте `samgr` открывает `/dev/binder` и регистрируется в драйвере как менеджер контекста. Сервис работает от пользователя `samgr` (uid 5555), а устройства binder имели права `crw-rw---- root root`. Права на файлы устройств выставляет `ueventd` по файлу `/system/etc/ueventd.config`. Важно не путать два файла: `/system/etc/init/ueventd.cfg` — это конфиг init, описывающий запуск самого сервиса `ueventd`; `/system/etc/ueventd.config` — конфиг ueventd с правами и владельцами устройств (`/dev/binder 0666 0 0` и т.п.). Правила для устройств конкретной платы можно дополнительно положить в `oneir/rootfs/vendor/etc/ueventd.config`: ueventd читает оба файла.



# Модули ядра и их автоматическая загрузка

## Зачем модули

Драйверы, встроенные в ядро (`=y`), запускаются при старте ядра, до монтирования корневой файловой системы. Драйверу, которому нужна прошивка или другие файлы с диска, в этот момент их взять неоткуда. Кроме того, универсальный образ, рассчитанный на разное железо, не может встроить в ядро все возможные драйверы и прошивки. Поэтому драйверы конкретных устройств собираются модулями (`=m`) и загружаются после старта системы, а в ядро встраивается только то, что нужно всегда.

## Сборка модулей

Сборка ядра OpenHarmony (`kernel.mk`) вызывает только цель образа ядра (`bzImage`), поэтому модули по умолчанию не собираются. Патч [linux_kernel/0007-kernel.mk-build-and-install-kernel-modules.patch](https://github.com/Harmony-Oneir/oneir_patches/blob/main/linux_kernel/0007-kernel.mk-build-and-install-kernel-modules.patch) добавляет после сборки ядра два шага:

* `make modules` — сборка всех модулей, отмеченных `=m` в конфигурации ядра;
* `make modules_install` — установка модулей без отладочных символов вместе со служебными файлами `modules.dep` (зависимости модулей) и `modules.alias` (какие устройства обслуживает каждый модуль).

Результат: `out/kernel/src_tmp/modules/lib/modules/<версия ядра>/`.

## Модули и прошивки в образе

Скрипт сборки образа копирует модули в `/system/lib/modules/`. Так как `/lib` — ссылка на `/system/lib`, модули доступны по стандартному пути `/lib/modules/$(uname -r)/`.

Прошивки устройств не входят в сборку ядра: это двоичные файлы производителей, которые распространяются отдельно, в репозитории `linux-firmware` (kernel.org). Для их установки используется отдельный репозиторий [firmware](https://github.com/Harmony-Oneir/firmware). Сами прошивки в нём не хранятся: манифест `linux-firmware.xml` описывает, какую версию `linux-firmware` скачать, и `repo` скачивает её в подкаталог `oneir/firmware/linux-firmware/`. 

По образцу x86-эмулятора OpenHarmony (`device/qemu/common/virt_full/kernel/firmware`) каждая нужная прошивка ставится целью `ohos_prebuilt_etc` из `oneir/firmware/BUILD.gn` (группа `oneir_firmware`, сборка: `./make.sh oneir/firmware:oneir_firmware`) в `/lib/firmware` — стандартный путь, где ядро ищет прошивки, поэтому дополнительные параметры ядра не нужны. Подкаталог внутри `/lib/firmware` задаётся так, как его ожидает драйвер: например, `ath10k` ищет файлы в `ath10k/QCA9377/hw1.0/`, а `rt2800usb` — прямо в `/lib/firmware`. Чтобы обновить прошивки, достаточно поменять версию (`revision`) в `linux-firmware.xml` и выполнить `repo sync`.

## Автоматическая загрузка

### Что есть в OpenHarmony

В OpenHarmony 7.0 нет механизма загрузки модулей под найденное железо:

| Механизм | Загрузка модулей ядра |
|---|---|
| init | Только явная команда `insmod <путь>` в конфиге платы |
| `ueventd` | Нет: поле `MODALIAS` из событий устройств не читается |
| HDF | Нет: управляет только своими драйверами и HDI-сервисами |

Для плат с заранее известным железом это нормальная модель: список модулей прописывается в конфиге платы. Для универсального образа нужен подбор драйвера по железу.

### Как работает доработка ueventd

Патч `init/0001-ueventd-load-kernel-modules-by-MODALIAS.patch` добавляет в `ueventd` подбор и загрузку модулей:

1. Каждое устройство сообщает ядру свою «подпись» (`modalias`), и она приходит в событии подключения в поле `MODALIAS`;
2. При первом таком событии `ueventd` загружает таблицу псевдонимов из `modules.alias`;
3. Для события `add` подпись сопоставляется с шаблонами из таблицы, и находятся подходящие модули;
4. Модуль загружается вместе с зависимостями из `modules.dep` (сначала зависимости, затем сам модуль) системным вызовом `finit_module`.

Особенности:

* при старте `ueventd` повторяет события для всех уже найденных устройств, поэтому модули загружаются и для устройств, подключённых до загрузки, и для подключаемых позже;
* загрузка идёт в отдельном процессе, чтобы медленные модули (например, ждущие прошивку) не задерживали обработку событий;
* каждый модуль запрашивается не более одного раза;
* `ueventd` получает привилегию `CAP_SYS_MODULE`;
* если файла `modules.alias` нет, автозагрузка отключается с предупреждением в журнале.

### Ограничение

Автозагрузка работает только для **устройств**: модули, не связанные с железом (например, модули `netfilter` для правил `iptables`), по `MODALIAS` не загружаются. Обычно ядро запрашивает их само через вспомогательную программу `modprobe`, которой в образе нет. Такие модули нужно либо встраивать в ядро, либо загружать явным списком при старте.

## Проверка

```sh
dmesg | grep -i "Module autoload"
lsmod
```

В журнале должно быть число загруженных псевдонимов и строки `loaded ...` для модулей найденных устройств, а в `lsmod` — сами модули с зависимостями.
