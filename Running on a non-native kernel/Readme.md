# Введение
Ключевая сложность запуска Open Harmony на обычном ядре линукса заключается в различии IPC. На самом фундаментальном уровне транспорт один и тот же. OpenHarmony IPC на стандартных устройствах опирается на драйвер Binder (binder_linux), который изначально пришёл из мира Linux/Android. Однако то, как этот транспорт подается разработчику и как устроена архитектура поверх него, кардинально различается. 
В классическом Linux процессы общаются через примитивные каналы связи — сокеты, файлы, каналы. 

**Как это выглядит**: Процесс А берет кусок памяти, сваливает туда пачку байтов и отправляет её в сокет. Процесс Б с другого конца этот массив байтов вылавливает.

**В чем проблема**: Ядро Linux и сам механизм IPC вообще не знают, что вы передаете. Для них это просто безымянный поток единиц и нулей.

**Что ложится на плечи разработчика**: Вы сами должны придумать свой собственный протокол: «Первые 4 байта — это тип команды, следующие 20 байт — строка, а дальше JSON». Вы сами пишете код для сериализации, десериализации, обработки ошибок рассинхронизации потока и проверки типов.

OpenHarmony берет тот же самый драйвер ядра (Binder), но строит поверх него мощный каркас, который меняет саму парадигму общения.

**Как это выглядит**: Вы мыслите не байтами, а объектами и методами. У вас есть удаленный сервис, и вы вызываете его функцию точно так же, как локальную: `service->DownloadFile("image.png", priority)`.

**Как это работает**: Фреймворк сам берет ваши аргументы, аккуратно упаковывает их в специальный контейнер, передает через ядро, а на стороне сервера автоматически распаковывает и вызывает нужный метод с уже готовыми переменными.

**Главная магия**: Самое крутое — если этот сервис находится не в соседнем процессе на вашем компьютере, а на другом устройстве (например, смартфон управляет умной колонкой), код вызова не меняется вообще. Система сама прозрачно перенаправит вызов через сеть. В Linux для этого пришлось бы писать полноценный сетевой клиент-сервер на TCP/IP, gRPC или REST API.

В нашем случае данный механизм является ключевым препятствием для запуска Open Harmony на обычном ядре Linux. Полноценно заменить или задействовать механизм Binder на обычной Linux нельзя исключительно на уровне пользовательских программ, если этого драйвера нет в ядре. Поскольку многие сервисы опираются на Binder, решить вопрос с его совместимостью является ключевой задачей для дальнейшего развертывания системы.

На текущий момент сборка ядра не понадобится. Вместо этого в качестве транспорта будет использован штатный binder_linux предусмотренный ядром операционной системы, который можно включить следующей командой:

```bash
sudo modprobe binder_linux devices=binder
sudo chmod 666 /dev/binder          # иначе только root
```

После этого в системе появляется файл устройства `/dev/binder`, через который и будет работать IPC OpenHarmony.


# AccessTokenManager (ATM)
AccessTokenManager — системный сервис с SA ID 3503. Через него в OpenHarmony проверяются права. У каждого процесса есть AccessTokenID, 32-битный идентификатор. В нём закодированы тип субъекта (HAP-приложение, нативный процесс или shell), версия и уникальный номер.

ATM отвечает на три вопроса:
* кто такой этот токен (тип приложения);
* какие у него права и в каком они состоянии (выданы, отозваны, выданы пользователем через диалог);
* как сохранить всё это между перезагрузками.

Вся эта логика живёт в пространстве пользователя. Но ATM лишь отвечает на вопрос «есть ли у токена X право Y». Само значение X ему должен сообщить тот, кому нельзя соврать. Этим занимается ядро.

В ядре OpenHarmony есть доработка, которой нет в обычном ядре Linux, а именно драйвер `access_tokenid`. Это misc-устройство `/dev/access_token_id`. Оно хранит в `task_struct` два поля:

* `token` — собственный токен задачи;
* `ftoken` — first caller token, токен первого звена цепочки вызовов. Если A вызывает B, а B вызывает C, то C может узнать, что всё началось с A. Это нужно privacy-подсистеме, чтобы записывать использование чувствительных прав на исходное приложение, а не на промежуточный сервис.
